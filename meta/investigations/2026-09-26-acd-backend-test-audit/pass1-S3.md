## Rule feedback

1. **Private helpers as the test interface.** Rule: "Use an existing stable production interface that a real caller uses at the selected level. Do not expose private code…" Example: about 60% of test_slack_bridge.py calls or monkeypatches `_render_thread`, `_dispatch_retry`, `_perform_journaled_message`, `_merge_turn_snapshot`, `_prepare_render_target`; test_app.py calls `_terminal_http_error`, `_browser_record_out`, `_continue_repaired_chats`. A strict reading makes ~70 tests Repair; I kept them because each private function is the single owner of its rule and no public entry reaches it in isolation. Proposed wording: "At unit level, a module-private function is an acceptable interface when it alone owns the rule and no public entry reaches it in isolation. Do not assert on private state or private call order when a public observation exists." Confidence 0.80.

2. **Static structure checks vs the change-detector definition.** Step 2 accepts "static check" as evidence; Step 3 says "A change-detector test fails after an internal refactor even though behavior remains correct. Do not add one." test_app.py:7253 regex-parses `_handle_frame` for `isinstance(parsed, X)`; a refactor to a dispatch dict fails it with behavior intact. test_slack_bridge.py:5732 traps the private name `_reindex`. The rule gives no way to tell a legitimate static guard from a change-detector. Proposed: "A static check is valid when the structure it reads is the contract (a vocabulary, a forbidden import, a mirror). When it reads implementation shape, it must fail loudly, name the refactor that requires updating it, and have no cheaper behavioral alternative." Confidence 0.70.

3. **Sleeps outside races, and proving absence.** Rule (Races): "Force the intended interleaving and prove readiness with an event, barrier, or queue. Do not rely on sleeps or scheduler timing." Most violations are not races but waits for background work (15 bridge tests with `sleep(0.05)`), and the rule is silent on "nothing happened" assertions, which pass vacuously if the work has not run (test_slack_bridge.py:4724). It is also silent on mutual-exclusion proofs where the blocked party has no readiness signal (test_slack_audio.py:150). Proposed: move the sentence out of Races and add: "Wait for background work with an explicit completion signal. To assert that something did not happen, first prove the system reached the point where it would have happened." Confidence 0.75.

4. **Input-side tautology.** Rule: "A tautological test derives its expected result from the same implementation logic that produces the actual result." The legacy-row tests (test_slack_bridge.py:1347 etc.) derive the *input* (the "legacy" row) from the current builder, so recognizer drift toward the new shape goes undetected. Delivery tests (test_slack_delivery.py:67, :82) take the *expectation* from the production constant, which the definition arguably covers but does not say. Proposed: "Derive expected results, and inputs that stand for recorded or historical data, from the accepted source. When the source fixes a value, assert the literal at least once." Confidence 0.70.

5. **Unique protection depends on harness constants.** test_app.py defines `AUTH: dict[str, str] = {}` and passes `headers=AUTH` everywhere, so the dedicated tokenless tests (:828, :1362, :6023) duplicate their neighbours only while `AUTH` stays empty. The rules do not say whether to judge uniqueness against the harness as it is or as a future edit might make it. Proposed: "Judge unique protection against the current harness. If a harness constant hides a requirement, fix the harness instead of keeping duplicate tests." Confidence 0.55.

6. **Redundant presentation asserts inside broader tests.** Rule: "Do not add a separate UI text or presentation test when another test already proves the same behavior." Bridge integration tests (test_slack_bridge.py:4811 card title literal, :4899 exact text `"Continue\n\nAutomated\n\nAnswer."`) re-assert render output already pinned by test_slack_render.py:334/:377. The rule covers separate tests, not extra assertions, so I kept them. Proposed: "…or add presentation assertions to a higher-level test when a lower-level test already pins them." Confidence 0.50.

7. **Scope consolidation has no verdict.** Rule (Scope): "Group assertions and cases that protect the same behavior and fail for the same reason." Five one-case priority tests (test_slack_render.py:942-1008) and the post/upload legacy pair (test_slack_bridge.py:1347/:1392) are parallel cases of one rule, not duplicates. The brief's Merge verdict means duplicate protection, so these had no fitting verdict; I kept them. Proposed: say whether Scope applies only to new tests or also asks reviewers to consolidate existing parallel tests. Confidence 0.50.
