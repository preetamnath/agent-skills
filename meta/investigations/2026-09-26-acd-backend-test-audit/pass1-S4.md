## Rule feedback

1. **A pinned literal copy counts as "parity".** Rule, Step 3: "A change-detector test fails after an internal refactor even though behavior remains correct." The rules do not separate (a) a parity check between two independently maintained artifacts from (b) a test that re-types the implementation's constant as a literal. The repo's "literal round-trip exemption" encourages (b). Examples: `test_schedules_mirror.py` (the literal set duplicates `app.py:1440` and misses the drift it names), `test_ttlcache.py:114`, `test_config.py:57`, the `test_gen_types.py` field lists, and the npm version in `test_test_suite.py:112`. Proposed Step 3 line: "A parity test compares two independently maintained artifacts. A literal copied from the implementation into the test is a change-detector unless the literal itself is the accepted source." Confidence 0.8.
2. **An accepted source exists, but the path is unreachable.** Step 1 accepts "a requirement, acceptance criterion…". Step 2 says: "Find any production export, flag, or wrapper that only this test uses, and remove it with the test." AC-016-14 (chat deletion cascades) is accepted, but `sessions.delete_chat` has no production caller. Step 1 says keep; Step 2 says remove. `test_digest.py:644` is the same case framed as a "latent hazard", and the rule "A reachable edge case … is not speculative" does not say what to do when the path is unreachable. Proposed Step 1 line: "If the only path to the behavior has no production caller, ask whether the requirement is live. Mark it Investigate. Do not keep or remove it on the AC alone." Confidence 0.8.
3. **Insensitive assertions go unnoticed in review.** Step 4 requires a proof only for *admitted* tests. For existing tests, "Before you remove or merge" is the only review checklist, and nothing tells a reviewer to check that the test's input reaches the guarded branch. Examples: `test_browsers.py:2313` (the same exception type comes from an earlier branch) and `test_stt_service.py:767` (the queue wait never exceeds the deadline, so the named branch never runs). Proposed Step 2 review line: "Confirm the test's input reaches the guarded branch, and that no other branch satisfies the same assertion." Confidence 0.75.
4. **Private state as a readiness or proxy assertion.** Step 3: "Prefer observable outputs … Assert a call, order, or interaction only when that interaction is required behavior." The rule is silent on reading private attributes (`_lock.locked()`, `_hub`, `_frame_epoch`), both when an observable alternative exists (browsers relay) and when none is cheap (lock-free sink). This led to low-confidence verdicts. Proposed line: "Read private state only when no public interface can observe the behavior, and say why in the test." Confidence 0.65.
5. **Two different versions of the global rule.** The `~/.codex/AGENTS.md` file on disk says: "…distinguishes a required behavior **or contract** … preserve that behavior **or contract**." The copy injected into this session (and quoted in the brief's scope) says: "…distinguishes required behavior from a plausible, material defect…". Contract-only guards (openapi error envelopes, CLI field spellings) are valid under one text and ambiguous under the other. Proposal: sync the two copies to the "or contract" wording, which is also the SKILL.md wording. Confidence 0.9.
6. **Scope versus Merge for a shared code path.** Step 3: "Group assertions and cases that protect the same behavior and fail for the same reason." The rule does not say whether one command-level test per CLI verb is "the same behavior" when all verbs share one handler (`scripts/acd:1073`). Proposal: "Treat one shared code path as one behavior. Keep a separate case only for a distinct handler." Confidence 0.5.
7. **Repository-hygiene and lint tests.** The Step 1 harm list ("broken user task, violated contract, corrupt data, weakened security or accessibility, or a repeated costly failure") does not clearly cover doc-citation rot, spec-tag conventions, or operator-instruction text (`test_backup_state_script.py`). I kept them under "repeated costly failure", with low certainty. Proposed addition to the harm list: "misleading durable instructions or documentation". Confidence 0.55.
8. **Cost-based repair.** Step 2.4: "unique protection worth its execution … cost". There is no guidance on when heavy fixtures that do not add sensitivity (11,000 files, 20,000 directories, nested runner re-running six tests) call for Repair rather than Keep. Proposal: "When a cheaper fixture (patched constant, fake clock) detects the same defect, repair the test to use it." Confidence 0.5.
